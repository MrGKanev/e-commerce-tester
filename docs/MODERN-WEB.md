## What runs in the tester

The tester implements a reviewed subset of [GoogleChrome Modern Web Guidance](https://github.com/GoogleChrome/modern-web-guidance). The installed skill supplies development guidance; the executable checks below actually inspect stores.

Implemented on 2026-11-17, against upstream revision `64a6d708f5a43f2cd3fde5d4d7db3905ba1bdf65`. This records the review source, not an update pin. The rule registry and implementation live in [tests/modern-web.ts](../tests/modern-web.ts); local fixtures are in [checks/modern-web.spec.ts](../checks/modern-web.spec.ts).

The passive inspector runs in **Full** (`43-modern-web.spec.ts`) for every configured inventory URL and in **Pages** on its existing document visit, including discovered inventory pages. Full/Modern Web additionally runs the guarded interaction and presentation probes described below; Pages stays passive. They support Shopify/WooCommerce and desktop/mobile projects. Full does not add discovered products to this suite; use Pages for those. Smoke remains unchanged. The control panel's existing Full and Pages selections include these checks.

```bash
# These commands visit the configured store.
pnpm test:modern-web --site=my-store
pnpm test:modern-web --site=my-store --project="Mobile Chrome"
pnpm test:pages --site=my-store

# Offline verification; no store requests.
pnpm build:css
pnpm test:modern-web:local
pnpm test:pages:local

# Additional engines, when installed locally (CI installs Chromium only).
pnpm test:modern-web:local --project=Firefox --project=WebKit --project="Mobile WebKit"
```

## Evidence and interpretation

Open the run's Playwright HTML report from **Reports**, expand a `modern web` or shared-page scenario, and open its attachments:

- `modern-web.txt`: findings with rule, severity, guide ID, element selector, observed facts and suggested fix.
- `modern-web.json`: schema version 1, URL, viewport, element counts, animation support/counts and structured findings.
- `modern-web-warning` annotations: recommendations are recorded even on passing scenarios.

Errors enter existing failed-scenario reporting/comparison. Recommendations do not reduce pass rate. Passing means the checks completed without a detected blocking error; review recommendations separately. There is no aggregate Modern Web score or automatic finding-resolution tracking yet.

The passive inspector reads the current main document and compares no-preference/reduce motion after two animation frames. It restores the originally observed preference in `finally`. This passive phase does not fill fields, submit forms, click controls, scroll or navigate a second time; the separate Full-only guarded probes below do focus and edit empty synthetic fields. The site may fetch its normal resources in response to media changes. Full adds one visit per configured URL; Pages reuses its existing visit. Existing pacing, rate-limit handling and browser fixtures remain active. Input values and form action URLs are omitted from evidence; page URLs/selectors still need the usual care when sharing reports.

## Limits of this first implementation

- The largest viewport image remains a heuristic. Where available, the separate foreground LCP entry supplies observed image attribution and timing subparts; restricted timing is null. No field INP is produced. Missing width/height attributes are not treated as layout defects: CSS or containers may reserve space correctly.
- Caption presence does not establish quality; absence may have an accessible external player or no meaningful audio. Decorative-video detection is heuristic.
- Motion covers currently running persistent spatial animations in the viewport. It excludes short/interaction-triggered states not currently running, canvas, animated images, flash limits and pause-button operation. Slower or changed-keyframe alternatives are accepted for review, not certified safe.
- No successful form submission is attempted. Guarded Full probes exercise bounded invalid/correction states; complete async validation and actual credential transport are not established. Error text may be generic. Missing references can be transient: confirm reproducibility before fixing the store.
- Hidden/disabled controls, shadow roots and iframes are outside the initial DOM scope. Empty/unsupported scope must not be read as comprehensive compliance.

## Partial-coverage implementation review — 2026-11-17

All original 32 Partial rows in the complete mapping were reviewed and updated with current evidence and remaining work. **One narrow instrumentation guide is Covered; 31 broader original guides remain Partial.** Two Pending topics (heavy-script attribution and progress naming) gained targeted partial coverage. Broad subjects such as accessibility, security and privacy are not marked complete from bounded automated samples.

Full/Modern Web still performs one configured page visit per scenario. After passive inspection it freezes subsequent HTTP requests, closes WebSocket routes installed before navigation, and captures/prevents submit events. It probes at most five empty supported required fields and five checkbox controls. Existing values are left untouched, including prefilled replacements after a rerender (covered by a regression fixture); no successful submit is attempted. Initial/invalid-blur/native-invalid/corrected states and Space-toggle reversal are recorded in `modern-web-interactions.json`/`.txt`. The guard is an HTTP/WebSocket test quarantine, not a general JavaScript sandbox. Network-dependent results are labeled unverified when traffic is blocked. It can intentionally prevent async validators from completing; their outcome is not a clean bill of health.

`modern-web-presentation.json`/`.txt` adds narrow and landscape reflow/occlusion, user text-spacing and 200% root-font stress, light/dark preference contrast/name samples and forced-color support/geometry observations. Temporary styles and preferences are restored. These probes are store test stimuli, not changes to the control-panel design. CSS injection or forced-color unavailability is recorded; it must not be read as a pass. They do not emulate a real OS font-size or virtual keyboard, certify all dynamic backgrounds, or test an authenticated theme preference.

The shared vitals attachment now records initial-visibility provenance and first-hidden time, observed LCP element/priority and available resource timing, event input/processing/presentation estimates, and optional long-frame/script/style/layout diagnostics. The presentation-delay estimate inherits Event Timing quantization. Resource restrictions/unsupported APIs stay explicit; this is not field INP. Passive sampling is finalized at `modern-web-probe-boundary` before our own motion, viewport and input stress begins, so those stimuli do not pollute loading metrics. Short passive windows can remain explicitly unmeasured and can fail strict mode; use an appropriate controlled performance profile rather than interpreting missing data as zero.

Dynamic overlay evidence (`dynamic-accessibility.json`) includes forward/reverse focus, explicit menu arrow advance, native light-dismiss outside/drag boundaries when supported, and manual/closedby=none policy observations. No arbitrary explicit close action is clicked. Native support gaps, absent outside space and developer-controlled workflows remain visible instead of becoming false failures. System back gestures, custom fallback scripts, submenu/typeahead and destructive/dirty-form decisions still need feature-specific contracts.

Verification for this expansion: 55 Modern Web fixture cases passed across desktop/mobile Chromium, Firefox and desktop/mobile WebKit; 10 vitals cases passed, including historical visibility/fallback and observed bitmap LCP; five dynamic accessibility cases passed in Chromium; shared-page and reporting acceptance passed. The actual `43-modern-web.spec.ts` entry ran against six local Shopify and five local WooCommerce URLs, attached all three evidence families and sent no probe writes to the fixture server. `pnpm check` passed with 90 unit tests. Navigation-timing calibration uses a real loopback HTTP response because mocked fulfillment can omit requestStart. No live stores or full acceptance-suite run were used.

## Maintenance process

1. `pnpm guidance:sync` refreshes the official skill/catalog at the start of relevant development tasks, as required by [AGENTS.md](../AGENTS.md). No maintained upstream-guide copy is committed. Store runs never download or execute the skill.
2. Search/retrieve current guidance for the area being changed. Compare it with this registry and the code. Upstream updates do **not** silently change store verdicts.
3. Update the shared implementation, the rule registry, the complete catalog mapping and their limits together. Recompute the guide-status summary when coverage changes. Preserve rule IDs unless their meaning changes. Bump the artifact schema version for incompatible structure changes.
4. Add local fixtures for both a real defect and a legitimate alternative. Keep heuristics advisory until a reliable behavioral assertion exists. Never validate a rule by submitting a real password/order or contacting a live store.
5. Run `pnpm test:modern-web:local`, `pnpm test:pages:local` and `pnpm check`. Modern Web fixtures run in `pnpm test:acceptance:local` in CI. Verify Shopify/WooCommerce and mobile spec discovery when adding/renaming suites.
6. Record the review date, upstream source revision and changed coverage here. Run metadata already records the tester's Git revision and working-tree state, tracing the executable expectations to our code.

The existing dialog/popover checks remain in `tests/a11y-dynamic.ts`, verified by `pnpm test:a11y:local`. Image load failures, axe, responsive overflow, Lighthouse and synthetic vitals retain their existing suites.

Initial implementation verification (before the partial-coverage expansion), 2026-11-17: all 20 local Modern Web fixture cases passed across desktop/mobile Chromium, Firefox and desktop/mobile WebKit. The shared-page integration passed with one document navigation and both evidence attachments. `pnpm check` passed, including 90 unit tests. Spec discovery was verified for Shopify and WooCommerce across all five production browser projects. No live store runs or full acceptance-suite run were performed for this implementation.

## Suggested implementation order

1. **Form feedback and input safety:** accessible-error-announcement, required-field-feedback, validate-input-after-interaction, select-menu-interaction, ime-safe-enter-submit and autofill-address-form. Reuse existing newsletter/checkout helpers, but validate good/bad cases locally without successful submissions.
2. **Loading evidence and attribution:** finish optimize-image-priority using actual supported LCP attribution, then add media deferral, preload/script-priority observations and long-frame script attribution. Keep heuristics advisory and mark unavailable browser observations explicitly.
3. **Interactive accessibility:** modal scroll containment, carousel pause/navigation and tabs; then keyboard/edge positioning for custom controls and overlays. Feature absence is not a defect.
4. **Security/privacy depth:** resource integrity/referrer hints and configured policy/consent lifecycle checks, with explicit platform parity. Controlled fixtures and scope contracts come before any invasive live probing.
5. **Broader resilience:** fonts/text scaling, theme/forced-color checks, shadow component behavior and optional SPA/scroll/gesture workflows. P2/P3 work remains conditional, not an instruction to add features to stores.

These waves group guide topics, not promised test counts. P1 is a starting order, not a claim that every P1 check applies to every store. Keep the existing nine rules and their evidence contract stable while expanding coverage.
